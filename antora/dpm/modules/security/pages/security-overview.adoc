== Security Principles

=== Defense in Depth

Multiple layers of security:

1. **Supply chain**: Secure dependencies
2. **Build**: Reproducible, auditable builds
3. **Runtime**: Secure execution environment
4. **Data**: Sensitive data protection

=== Least Privilege

DPM follows least privilege principles:

1. **Minimal permissions**: Only necessary access
2. **Sandboxed execution**: Limited system access
3. **Explicit grants**: No implicit permissions

=== Transparency

All security measures are transparent:

1. **Open source**: Full code visibility
2. **Dependency tracking**: Complete SBOM
3. **Audit trail**: Full activity logging

== Supply Chain Security

=== Dependency Management

DPM uses `cargo-deny` to enforce:

[cols="1,2", frame=none]
|===
| *Check* | *What It Validates*

| `advisories` | Known CVEs in dependencies
| `licenses` | Only approved licenses
| `bans` | Duplicate version warnings
| `sources` | Only trusted registries
|===

=== License Compliance

Only approved licenses are allowed:

[cols="1,1", options="header"]
|===
| License | Status

| MIT | ✅ Approved
| Apache-2.0 | ✅ Approved
| BSD-2-Clause | ✅ Approved
| BSD-3-Clause | ✅ Approved
| GPL-3.0 | ✅ Approved (DPM's license)
| ISC | ✅ Approved
|===

=== Vulnerability Scanning

Automated security audits:

1. **GitHub Dependabot**: Automated vulnerability alerts
2. **cargo-deny**: License and vulnerability checks
3. **CI integration**: Block merges on security issues

== Runtime Security

=== Sensitive Data Masking

DPM automatically masks sensitive data in debug output:

[source,lisp]
----
;; These variables are automatically masked:
;; - password, passwd, pwd
;; - token, secret
;; - api_key, apikey, access_key
;; - private_key, ssh_key
;; - auth, authorization, bearer, jwt, session

(debug)  ;; Shows: password = ******
----

=== Environment Isolation

DPM runs in a sandboxed environment:

1. **No direct system access**: All operations through DPM commands
2. **Type safety**: Rust's type system prevents many errors
3. **Input validation**: Arguments validated before use

=== Socket Permission Checks

Docker socket access is controlled:

1. **Socket detection**: Automatic socket location
2. **Permission validation**: Check socket permissions
3. **User verification**: Verify user has access

== Build Security

=== Reproducible Builds

DPM builds are reproducible:

1. **Locked dependencies**: `Cargo.lock` committed
2. **Deterministic builds**: Same input → same output
3. **Cross-platform**: Consistent across platforms

=== Binary Signing

Release binaries are signed:

1. **GitHub Releases**: Signed with GPG
2. **Checksum verification**: SHA256 checksums
3. **Signature validation**: Verify binary authenticity

=== CI/CD Security

GitHub Actions security:

1. **Limited permissions**: Minimal workflow permissions
2. **Secret management**: Secure secret handling
3. **Audit logging**: Full activity logs

DPM provides automatic security:

|===

Users can enhance security:

[cols="1,2", frame=none]

== Security Auditing

=== Local Auditing

Run security checks locally:

[source,bash]
----
# Check dependencies
cargo deny check

# Run clippy
cargo clippy

# Run tests
cargo test
----

=== CI Auditing

Automated security in CI:

1. **Commit validation**: Conventional commits
2. **Security audit**: cargo-deny checks
3. **License compliance**: License verification
4. **Build & test**: Comprehensive testing

=== Audit Trail

Full audit trail available:

1. **GitHub dependency graph**: Complete SBOM
2. **Commit history**: Full change history
3. **Release notes**: Detailed release information
4. **Security advisories**: Vulnerability reports

== Vulnerability Reporting

=== Responsible Disclosure

Report security issues responsibly:

1. **Email**: security@sunnyday-software.com
2. **GitHub**: Use security advisories
3. **Timeline**: 90-day disclosure timeline

=== What to Report

[cols="1,2", frame=none]
|===
| *Issue Type* | *Description*

| CVE | Known vulnerabilities in dependencies
| Security bug | Security-related code issues
| Design flaw | Security design problems
|===

=== Response Process

1. **Acknowledge**: Report acknowledged within 24 hours
2. **Investigate**: Issue investigated within 7 days
3. **Fix**: Fix developed and tested
4. **Release**: Patch released
5. **Disclosure**: Public disclosure after fix
